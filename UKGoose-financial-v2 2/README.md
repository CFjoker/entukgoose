# UKGoose 财务模型对齐版 v2

## 启动

在 VS Code 打开本文件所在文件夹，终端运行 `npm start`，浏览器访问 http://127.0.0.1:8787 。先在旧终端按 Control+C 停止旧服务。不要同时启动两个占用8787端口的版本。

微信开发者工具重新导入本文件夹中的 miniprogram，保留自己的 AppID。本机后端地址仍是127.0.0.1:8787。真实手机与正式发布需要部署HTTPS服务及真实身份认证；原型没有支付或物流接入。

## 与报表一致的计算

来源 UKGoose_Dynamic_Financial_Model_Revised.xlsx。backend/financial-model.json 保存输入、月份、源文件SHA256和对照结果；不是实时链接，Excel改变后须同步参数并复测。

- Inputs B15：商品价值5%服务费。
- Inputs B25:B32：重量组合加权含VAT每程运输成本 £8.0682，前端每条费用显示至便士。不是按用户实际重量的承运商报价。
- Profit & Cashflow H:I：整托盘向上取整，仓储月成本按月订单数分摊。6周平均停留、每月4.345周、每托盘6批货、£4.99/托盘/周。
- 物流100%用户承担；不加价。佣金才是留存服务收入。
- 平台承担包装10/24、支付手续费0.6%、每单拣货£1、索赔预算£0.25及当前为0的结款费。不向用户另加这些成本。
- 支付费基数为商品收款加物流收款，另加两次付款的固定费用。正式集成未验证，0.6%只沿用报表假设。
- 开发£561、年费£112.20、其他启动£45，及10%储备只进入内部现金预测，不添加到用户账单。Month 13续年费。

## 必须区分的原型推导

报表没有独立客户价目表：
1. 按实际日期报价时，使用所选模型月份的每单仓储额 × 实际天数/42。最低1天沿用v1。不是报表明确的逐日收费规则。
2. 一个lot按一个包裹、一份仓储量解释；多lot的两程运输和仓储同比例增加，佣金按整单商品价值只算一次。实际尺寸与重量限制仍需运营确认。
3. 报表只规定用户承担物流，未分配买卖双方。演示继续由买家承担物流与商品价，卖家另付5%服务费。卖家收到全额商品价，净所得扣除另付服务费。
4. 12单位容量、4单位/单、最长120天仍为演示限制，不能把月度托盘需求当作真实仓储供应容量。
5. 月份是Jun Y1–May Y3的相对预测序号，不强行对应日历年份。所选月份决定估价分摊，日期决定时长。

界面分项先四舍五入至便士再求总额；内部月预测保留完整精度，因此实际收款与按月总额先舍入的预测存在小额舍入差，不能要求逐单求和永远完全等于预测。

## 旧数据

沿用原文件夹已有data.json且不改旧报价。旧版未确认订单不能用新版规则直接审批，需重新申请；旧订单历史仍可查看。更新没有删除原文件夹或原表格。本副本为独立版本。

## 检查

`npm test`：11项测试，包括24个月20个字段逐项对照工作簿已存结果。管理员网页可查看完整月度现金预测；小程序显示报价所用月份与分摊依据。已做JS语法及计算测试，本轮未在微信开发者工具或真机验收。

大鹅及界面沿用v1。登录与管理员切换仍是本机演示身份；没有真实校园认证、托管支付、退款、图片上传及物流预订。
